## Design Specificity Verdict

The app has a specific product world: Binance-inspired dark slate, gold accents, mono numerals, dense portfolio data, and task-led tabs. It does not feel like a generic SaaS shell at the top level. The specificity weakens inside individual pages: many areas fall back to same-sized surface cards, repeated uppercase labels, and wide data tables with local one-off layout rules. The result is recognizably a crypto portfolio workstation, but not yet a fully authored workstation system.

## Overall Impression

The product direction is right, but the interface is still assembled from page-by-page solutions instead of a coherent responsive layout system. Desktop is close to the intended quant workstation; mobile is better after the bottom-nav change, but several components still solve overflow by scrolling rather than truly adapting. The biggest opportunity is to create a small set of responsive primitives for pages, card sections, data tables, metric groups, and mobile task flows, then refit all pages through those primitives.

## What's Working

1. **The visual world is coherent at shell level.** The dark slate, Binance gold, mono numerals, and fixed desktop sidebar establish the right use-scene for a portfolio workstation.
2. **The primary tasks are discoverable.** Dashboard, Inject, Rebalance, History, Narratives, and Settings map to real investor workflows instead of abstract product categories.
3. **Data density is appropriate for desktop.** Tables, drift bars, charts, and metric cards suit a user who wants precision rather than marketing-grade simplification.

## Priority Issues

### [P1] Responsive layout is patched, not systematized

**Why it matters:** Users on mobile will see fewer collisions now, but many components still rely on local inline styles, min-width tables, and emergency horizontal scroll. That prevents a consistently good mobile experience across Dashboard, Inject, Rebalance, Settings, History, and Narratives.

**Fix:** Build shared layout primitives: `PageStack`, `SectionCard`, `ResponsiveMetricGrid`, `DataScroller`, `MobileStack`, and `ActionBar`. Replace per-page max-widths and one-off grid rules with these primitives.

**Suggested command:** `$impeccable adapt all pages`

### [P1] Tables are still desktop-first data slabs

**Why it matters:** Horizontal scroll preserves data, but it does not make the task easy on a phone. Holdings, Inject result, Rebalance tables, History, and Narrative momentum need mobile-specific row cards or priority columns, not only scroll containers.

**Fix:** For mobile, convert high-value tables into stacked rows: top line = asset/narrative + score/value, second line = key deltas, third line = actions/status. Keep horizontal scroll only for advanced numeric detail.

**Suggested command:** `$impeccable layout tables`

### [P2] Navigation hierarchy is overloaded on mobile

**Why it matters:** Six bottom-nav items are visible at the same hierarchy level. This keeps all tabs reachable, but it makes mobile navigation feel cramped and weakens the primary Dashboard → Inject path.

**Fix:** Prioritize four bottom-nav destinations: Dashboard, Inject, Rebalance, Settings. Move History and Narratives into Dashboard secondary actions or a “More” destination, unless the user uses them as primary daily tasks.

**Suggested command:** `$impeccable shape mobile navigation`

### [P2] Component hierarchy is too even

**Why it matters:** Many cards, filters, stat blocks, and section headers have similar visual weight. In an operate-mode interface, users should immediately know what is primary, what is supporting, and what is advanced.

**Fix:** Define hierarchy tiers: page lead metric, task input card, primary table/chart, secondary insight card, metadata/helper copy. Apply size, spacing, and contrast from those tiers instead of repeating the same surface-card treatment.

**Suggested command:** `$impeccable layout all pages`

### [P3] Layout animations and progress bars animate expensive properties

**Why it matters:** Animating width, margin, and padding can cause jank, especially on mobile and lower-powered machines. This is not the main UX failure, but it undermines the workstation feel.

**Fix:** Replace width/margin transitions with transform/opacity where possible. For progress bars, animate transform scaleX from a fixed-width element instead of animating width.

**Suggested command:** `$impeccable optimize motion`

## Persona Red Flags

**Alex, power user:** Wants to glance, decide, and act. Red flags: no keyboard shortcuts for tab switching or refresh; mobile bottom nav has too many equal destinations; tables require horizontal scanning for frequent comparisons; primary Dashboard → Inject workflow is not visually promoted enough.

**Jordan, first-timer:** Wants reassurance that API keys, targets, and demo mode are safe. Red flags: API setup and target allocation rules are spread across Settings and explanatory copy; narrative signal availability/confidence may feel opaque; errors are visible but not always local to the exact data source that failed.

**Maya, mobile-first investor:** Wants to check portfolio and cash-injection guidance quickly. Red flags: some dense desktop tables remain the main representation; six bottom-nav items crowd the thumb zone; small chips and mono numeric labels can become hard to tap or compare when content gets long.

## Minor Observations

- The mobile hamburger is now hidden correctly, but its state still exists in `App.tsx`; it can be removed later to reduce dead mobile drawer logic.
- Mobile nav order differs from desktop sidebar order, which can create recognition friction.
- Narrative cards and detail panels carry strong information, but the lifecycle track and signal breakdown need tighter mobile treatment.
- Geist warning is acceptable under the current brief, but the app would feel more distinctive with a stronger non-default UI text face while keeping JetBrains Mono for numerals.
- A lot of layout lives in inline style objects, making consistent refinement harder.

## Questions to Consider

- What are the four actions the user actually needs on mobile every week?
- Should mobile tables become task cards while desktop remains table-first?
- What information deserves to be in the first viewport of every tab?
- Should “Narratives” be a primary tab, or an insight layer inside Dashboard?
- What would a truly confident cash-injection workflow hide until the user asks for detail?
